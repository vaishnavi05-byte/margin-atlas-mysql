## The decision

Target junior data analyst, reporting analyst, MIS analyst and junior BI roles whose degree and experience requirements fit. Make SQL, Excel, reliable data preparation, Power BI and clear business explanations the center of the portfolio. Use Python to make the work reproducible. Add advanced features when they support a useful decision.

For your e-commerce flagship, develop **Margin Atlas Decision Studio**, an original extension of your existing MySQL project. Its central question is: **Which category, region or acquisition-channel issue should the business investigate first, given limited capacity and uncertain recoverable contribution?** A decision workbench, explicit cost assumptions and an evidence trail will give it a different purpose from a general sales dashboard.

## Original flagship implementation brief

**Margin Atlas Decision Studio** will extend your current MySQL project with a decision workflow for contribution leakage. Its intended audience is a finance/operations manager who can investigate only a few issues each week. It will distinguish an observed pattern, an uncertain hypothesis and a fixed-demand scenario.

### Native Power BI report experience

1. **Business pulse:** Net sales, contribution, comparable-period change and a readable revenue-to-contribution bridge. Metric/dimension switching changes a useful analysis, with units and filter context visible.
2. **Leakage explorer:** Category-region comparisons, discount/refund/cost drivers and drillthrough to order detail. Marketing-dependent measures are unavailable at unsupported product/category grain.
3. **Delivery investigation:** Mature returns and delivery eligibility, trend comparisons and transparent sample sizes. Associations prompt investigation rather than claims that delays caused returns.
4. **Customer cohorts:** Complete 90-day windows, count-based weighted totals and cohort drillthrough. Observed historical contribution is not labeled lifetime value.
5. **Decision workbench:** Rank non-overlapping candidate segments under explicit sample/coverage rules; show contribution exposure, evidence, owner and next diagnostic step. Selecting a candidate reveals the source rows and definition.
6. **Scenario and data trust:** Cost/return assumptions, break-even intervention cost and sensitivity comparisons, alongside refresh time, row counts, exclusions and SQL-to-DAX checks. Hypothetical recovery is never labeled realized savings.

Use a new visual system with strong hierarchy, restrained color, consistent navigation, contextual tooltips, reset bookmarks and accessible labels. Native bookmarks/drillthrough and field parameters support these interactions; they must be tested in the actual report. [S10, S16, S17]

### Analytical and delivery requirements

Keep MySQL as the declared warehouse. Add reviewed SQL marts and Python modules that read the project's own data; document table grain and every allocation. Separate marketing spend at date/channel grain from category/region contribution before marketing. Preserve zero-order spend dates. Use integer minor units for financial checks and ratio-of-sums measures.

Start the decision workbench from a mutually exclusive category-region partition. Apply configurable minimum sample sizes. Rank operational exposure first. If an assumed recovery rate is entered, calculate scenario contribution and break-even cost separately; do not call the ranking causal uplift or a production prediction. Avoid adding overlapping candidate totals.

GitHub delivery should include setup commands, metric definitions, original design notes, screenshots, tests, CI, and a short case-study memo. A browser companion may help reviewers explore, but it must be explicitly labeled as separate from native Power BI. Do not describe generated PBIP files as a working PBIX or a published report.

### Completion gates and interview proof

The new project enters the resume only after: reproducible pipeline and SQL checks pass; Power BI opens and refreshes; key DAX totals match SQL; slicers, drillthrough, bookmarks and empty states work; screenshots are reviewed; and the repository/demo destinations are verified. GitHub and Power BI connections were not confirmed at this review.

Interview practice should cover: preventing join fan-out; defining the denominator; debugging filter context; explaining a query plan; distinguishing contribution from profit; challenging a scenario assumption; and rebuilding one query, one pandas transformation and one DAX measure without copying. A strong portfolio supports that demonstration; it does not establish independent proficiency by itself.
